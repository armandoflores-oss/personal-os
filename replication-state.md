### Phase 6 — The loop: reconcile, grade, self-retire → `IN PROGRESS (all built; never run unattended)`
Nightly cloud routine after data-in, before brief: prepare (deterministic evidence gathering) → judge (model: hard closes / soft proposals / drop ambiguous) → apply (guardrails in code: id validation, firewall demotion, ~15 mutation cap, idempotency stamp, proposals ledger with 72h aging and permanent vetoes) → grade (deterministic 0-10, idempotent, distinguishes user events from system events). Weekly pass: promote recurring corrections into rules (one commit each); low-risk upgrades auto-apply, structural ones render as numbered proposals in the brief. Self-retirement at 21+ days of trend data.
- **Built 2026-09-24 as `scripts/loop.py` + routine `loop-personal-os`, cron `30 18 * * 1-5`.** Timing chosen against the real constraint, not the spec's wording: the last ingest is 17:45 and the brief is 09:00 next day, so 18:30 sits after the day's data and before the brief while the laptop is still awake. A pre-dawn slot would read better on paper and fire late on wake, as the 07:00 brief did for a week.
- **Only stage 2 is a model, and it only labels.** Prepare gathers evidence mechanically (what Armando said, what a recent transcript says, 14+ days without movement); judge classifies `dura`/`blanda`/`ninguna` over evidence it did not choose; apply and grade are code. A model that gathers its own evidence and then rules on it can talk itself into anything.
- **Cap = 6 mutations/night, chosen from Armando's numbers.** The system closes ~0.5 tasks/night on evidence (11 outbound closes in three weeks) against ~14 open. Six is four times a normal night, so it never gets in the way, and under half the board, so a bad night is a reversible annoyance rather than a wipe. The spec suggested ~15; at this board size that is not a cap, it is permission to empty it.
- **All four guardrails verified by trying to break them:** a fabricated task_id was rejected; 10 hard decisions produced exactly 6 closes and 3 cap rejections; re-applying the same decisions file returned `ya_aplicado` off its hash stamp; and a deliberately firewalled task marked `dura` came out as a 72h proposal with `degradada: dominio firewalled`, still open. The six real tasks closed during the test were reopened with new events, not by editing the log.
- **Every close carries evidence and its undo** in the brief: the evidence line, then `↩︎ reábrela con \`T-40 no\``. Proposals render with their close date and both one-word answers (`va` applies now, `nunca` kills it forever).
- **Bug found by rendering it:** the loop wrote receipts with `fecha` but no `ts`, and the brief filters receipts by `ts` — so everything the loop did was silently dropped from the brief. Fixed.
- **Proposals ledger, 2026-09-24.** Runs inside `loop.py apply` and in `brief-pre` rather than as its own command, so it costs no new tool approvals. Four behaviours, all tested in one pass: a proposal waiting, one vetoed the moment Armando touched the item, one aged out and closed with a receipt, one firewalled that did not age at all. Re-proposing a vetoed item returns `vetada para siempre`.
- **A firewall leak caught by rendering it:** the first version of the proposals section printed the code and title of a firewalled proposal. A retained proposal showing its title is the same leak as showing the card, just in a different section — firewalled proposals are now a count-only line with no code, no title and no date.
- **Claude wrote a fake `actor: "user"` event while testing veto detection** — exactly the grader poisoning the actor field exists to prevent. Neutralised with a `system:limpieza` note on the same task rather than by editing the log; it will still count as one user intervention in today's grade.
- **Weekly pass built 2026-09-24**, routine `semanal-personal-os`, Fridays 18:45 after the loop. `scripts/weekly.py cluster|promote|upgrade`.
  - **Clustering compares word STEMS, not whole words.** The first version missed a third correction in the same cluster because "correos" did not match "correo"; with 5-letter stems it correctly found clusters of 4 and 3 in the real week. The script proposes token-clusters and the model reviews the singles for the ones that say the same thing in different words — that part a deterministic clusterer cannot see.
  - **One commit per promoted rule**, verified: two rules produced two separate commits, either revertible alone.
  - **Risk split is mechanical, not a judgement call.** Low risk = a number on a short allowlist inside `loop.py` only (`MAX_MUTACIONES` 1-12, `VENTANA_PROPUESTA_H` 24-168), changed by regex, self-committed, receipted in the brief. Verified: an in-range change applied itself, an out-of-range one was rejected. Everything else is structural, gets a number in the brief, and is accepted with `aplica 2` or killed with `mejora 2 nunca` — `reply.py` now understands both.

- **Self-retirement built 2026-09-24**, inside `grade` so it costs no new approvals. At 21 days of trend data it compares the median of the first 7 against the last 7 on three numbers chosen from Armando's side of the table, not the system's: how often he intervened, how many items stay open, how many closes came back. Improving → one line in the brief. Not improving → the loop proposes its own shutdown with the numbers side by side.
